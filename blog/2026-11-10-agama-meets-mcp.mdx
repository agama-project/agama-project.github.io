Whether you are installing openSUSE on a workstation, managing SLES servers across hardware
generations, or orchestrating bare-metal deployments with Uyuni, Agama introduces a new way to
install Linux. By embedding a Model Context Protocol (MCP) server directly into the live installer
environment, Agama becomes the first AI-ready OS installer. Without running an LLM inside the
installation media, it exposes hardware probing, configuration validation, proposal calculation, and
systemd logs as standardized tools—allowing external AI assistants and orchestrators to safely
inspect hardware, prepare valid configurations, and monitor installations under strict,
deterministic guardrails.

Traditional automated installation relies on static profiles or templating—such as AutoYaST rules
and classes, ERB templates, pre-scripts, or dynamic [Jsonnet](https://jsonnet.org/) profiles. While
flexible, anticipating hardware variations up front requires maintaining extensive declarative
logic. Agama's MCP server takes a different approach by exposing the installer's state machine to
external agents over a standard protocol.

## Two main use cases {#use-cases}

Agama's MCP server is designed around two distinct scenarios:

### 1. Assisted configuration creation (Human-in-the-loop) {#use-case-assisted}

In configuration mode (`inst.mcp=config`), an AI assistant helps generate a valid installation
profile from natural language (for example: _"Select openSUSE Tumbleweed with GNOME desktop, use
Btrfs on the NVMe disk, and set up user tux"_). The agent inspects hardware inventory, checks schema
constraints, drafts the profile, and asks Agama to calculate the proposal.

Destructive operations like disk formatting and rebooting are disabled in this mode (returning HTTP
403), and pre-installation scripts are rejected. The human operator reviews the resulting proposal
in Agama's Web UI and starts the installation manually.

### 2. Autonomous AI orchestration (Full automation) {#use-case-orchestration}

In full mode (`inst.mcp=full`), an external orchestrator (such as Uyuni or an automated bare-metal
pipeline) can drive the deployment end-to-end. The orchestrator probes hardware, generates the
profile, validates the proposal, and triggers disk formatting and package installation
(`commit_install`). It can also answer interactive installer prompts (such as disk encryption
passwords or GPG keys), monitor progress events, inspect logs if an error occurs, and reboot the
machine into the new system.

## Deterministic guardrails {#guardrails}

Operating system installation is an inherently destructive operation. Because language models can
hallucinate device names or configuration options, Agama does not grant shell access or run raw
partitioning tools. Instead, all interactions pass through deterministic safety layers:

### Schema validation {#schema-validation}

Every profile submitted by an AI client must strictly conform to Agama's JSON Schema. The agent can
inspect schema definitions dynamically per subsystem (`storage`, `software`, `network`, `user`,
`bootloader`) via the `get_config_schema` tool. Unknown keys or invalid types are rejected
immediately before reaching any installer subsystem.

### Proposal verification and self-correction {#proposal-verification}

Setting a configuration does not write to disk. Instead, Agama calculates a proposal against the
detected hardware. If the agent requests an invalid configuration—such as allocating more space than
a disk has or selecting conflicting software patterns—Agama rejects it with structured diagnostic
issues. The agent receives a clear error description and can adjust its profile before any disk is
touched.

### Operating modes and token isolation {#modes-and-security}

The MCP server is disabled by default and must be explicitly enabled on the kernel command line
(`inst.mcp=config` for configuration only, or `inst.mcp=full` for autonomous deployment). To prevent
an agent from using its token to call general REST endpoints, Agama enforces strict token isolation:
the dedicated MCP token only grants access to `/mcp` and is rejected by the rest of the API.

### Observability {#observability}

To keep external agents informed without flooding their context with raw console output, the server
provides targeted diagnostic tools. Agents can query scoped systemd journal logs (`get_logs`) for
installer, package manager, or system units, track progress without busy polling (`wait_progress`),
and answer interactive prompts (`answer_question`).

## Try it out and check the docs {#next-steps}

The embedded MCP server will be included in the upcoming **Agama 26** release, and is already
available in the
[systemsmanagement:Agama:Devel](https://build.opensuse.org/project/show/systemsmanagement:Agama:Devel)
OBS repository and nightly live ISOs.

You can test it today on a virtual machine or test hardware by booting with `inst.mcp=config` and
connecting an MCP-compliant client (such as Gemini CLI, Claude Desktop, or Cursor).

For complete setup instructions, client configuration examples, and token details, check out the
[Agama MCP README](https://github.com/agama-project/agama/tree/master/rust/agama-mcp#security--token-isolation).
